The approach

A small framework for a wider canvas.

Prastora explores a simple idea: let a website's proportions follow the screen, while keeping the structure flexible and the implementation light.

In this article

The short version

A viewport-linked rem scale, reusable layout primitives and complete page examples. Keep the core separate from the theme, and use native HTML interactions where they are sufficient.

Start with the screen, not the container.

Many websites place their content inside a fixed maximum-width container. As the viewport grows, the central column stays much the same and the empty space around it expands. That is often a deliberate and useful choice. It is not the only possible starting point.

Prastora began with a different preference. On a large display, content should be able to grow with the available space rather than remain a small island in the middle. Typography, spacing and visual elements can share a scale, preserving much of the composition as the screen changes.

The goal is not to fill every pixel with information. A page still needs breathing room, a clear hierarchy and sensible reading sections. The difference is that surrounding space belongs to the design's proportions, rather than being whatever remains after a fixed-width layout has stopped growing.

A preference, not a universal rule

A dense application, a reference document and a commercial landing page may need different treatments. Prastora is an experiment in one approach, developed through concrete pages rather than a promise that every design problem has already been solved.

That is why the examples matter. A grid in isolation tells you little about a long heading, a detailed article or a product with several characteristics. Complete pages make it easier to see where the approach helps and where it needs adjustment.

One scale. Several compositions.

The root font size is linked to viewport width. Sizes expressed in rem follow that value, so the same mechanism affects typography, spacing and component dimensions. CSS variables make the scale and surrounding design choices available in one place.

This does not mean shrinking a desktop page until it fits a phone. Responsive composition remains necessary. Two columns can become a single reading column, navigation can move into a disclosure, and a catalogue can retain a compact arrangement where an article uses one column.

Scaling controls the proportions. Responsive layout controls the arrangement. A useful page needs both.

The current examples use separate scale settings for mobile, desktop and wider screens. Those settings are visible in the CSS rather than hidden inside a runtime. They remain design decisions to review, not fixed rules that every project must inherit.

Review the reading experience on real devices

A computed font size is useful evidence, but it is not the entire reading experience. Device settings, display density, browser behaviour and the visitor's needs affect what feels comfortable. Review paragraphs, smaller labels and actions separately instead of assuming one adjustment will improve everything.

Viewport-linked typography deserves careful zoom testing. It can counteract part of a browser zoom change, and breakpoint transitions can produce abrupt size changes. These are current trade-offs to refine, not capabilities Prastora claims to have already perfected.

An optional minimum scale variable provides a place to experiment with a lower limit. It is not enabled by default, keeping the current examples close to the original proportional approach. The audience of a real site should guide the final choice.

Let content define its own height.

Short and long headings should both fit without arbitrary clipping. The same applies to paragraphs, captions and descriptions. Ordinary document flow and flexible grid tracks allow content to establish the space it needs.

Stacks handle the rhythm between successive elements. The prose component handles headings, lists and quotations. Cards provide a boundary when a group of information benefits from one, without requiring every section to be boxed.

  • Use headings to establish a clear reading hierarchy.
  • Keep paragraphs in a continuous flow, with enough space to distinguish one idea from the next.
  • Use lists when information genuinely consists of separate points.
  • Add supporting cards where they help visitors choose a next step.

Align related rows only when they are related

Adjacent cards sometimes contain parallel lists. If one point wraps while its neighbour is short, independent lists can lose their common rhythm. The optional aligned pattern uses CSS subgrid to share corresponding row heights, with text and markers centred within each row.

This is a specific pattern, not the default behaviour of all cards. It assumes a heading followed by a matching number of list items. Unrelated descriptions and editorial lists should use their natural flow instead.

  1. Choose the simplest composition that expresses the relationship between the content.
  2. Introduce shared alignment only when readers benefit from comparing corresponding points.
  3. Review longer wording and translations before deciding that every item must stay on one line.

Separate structure from identity

The core stylesheet contains layout primitives and the basic text system. The theme provides the visual character of the examples. Separating the two makes it easier to change colours and presentation without turning every page into a special case.

Variables describe shared choices: scale, type sizes, spacing, colours and a few component settings. They do not need to replace every number. A local rule can remain local when it does not represent a reusable design decision.

Use media without making the page depend on it.

An image can explain or add context. It should not be necessary just to hold the surrounding layout together. The media component provides a predictable frame while the figure and caption remain ordinary HTML.

The artwork uses a local SVG sprite. A site can use photographs or diagrams with the same surrounding structure. Asset choice still matters for loading speed; a small stylesheet cannot compensate for unnecessarily large media files.

Prefer the platform when it does the job

Native details and summary elements provide disclosures without a JavaScript dependency. Links provide navigation. Form controls provide familiar input behaviour. Additional scripts remain an option when they deliver a concrete interaction benefit.

Video players, map services, enquiries and checkout belong to the site that needs them. A visual pattern is not an application backend. Keeping those concerns separate allows a simple page to remain simple.

Build-time tooling is a different consideration. Generating shared headers or translated pages before deployment does not require visitors to download that tooling. A future build process can preserve the same lightweight output.

Build a useful foundation, then refine it.

The examples cover an overview, a service composition, a long-form article, a catalogue, a detail page, pricing, a gallery and contacts. Together they exercise common relationships between navigation, text, cards and media without committing the toolkit to one site's content structure.

Logical properties and text-direction checks are part of the foundation. They do not yet amount to a translation system. Localised page identity, language switching and translated interface text will need their own implementation when a site requires them.

The direction is deliberately modest: keep reusable parts small, add page patterns when they solve a real need, and review results on screens people actually use. Prastora should make a site easier to assemble and adjust, not prescribe an entire application architecture.
